# clobber-scan

Static detector for **DOM clobbering of global variables and `document`
properties** by user-controlled HTML.

It answers one question precisely: *can an element that an attacker is able to
inject into this page shadow a name that the page's own scripts read, and does
the resulting value reach a dangerous sink?*

```
$ npx clobber-scan spec.json
DOM clobbering scan — engine model measured 2026-11-21
scripts=1  reads=5  regions=2  findings=3

== Clobbered config global (1) ==

  [CRITICAL] APP_CONFIG  — impact: url-load
      read:   bundle.js:5:12 (window-property)
      where:  all engines
      inject: <span id="APP_CONFIG">  (region: description, reviews)
      why:
        - no window property exists for this name, so the window.X lookup falls through to named access
        - named element is reachable in every measured engine
        - a clobbered value reaches a URL/script sink, so an attacker-supplied element can choose the loaded resource
      ...
```

## What problem this solves

A page renders user HTML through a rich-text field, a comment list, or a
templated attribute. A sanitizer strips `<script>`, so the obvious XSS is gone.
But the attacker can still write:

```html
<img name="APP_CONFIG">
```

If the page then does:

```js
var cfg = window.APP_CONFIG || {};
script.src = cfg.cdn;          // cfg is now an <img> element
```

…the application reads attacker-influenced content as configuration. The same
works for `document.cookie`, `document.getElementById`, and hundreds of other
`Document` members.

The rules are subtle, differ between browsers, and depend on how the script
declares the name. This tool encodes the measured rules and reports only the
combinations that are actually reachable.

## Why the rules are hard

Three things make this a real problem rather than a regex:

1. **`window` and `document` behave oppositely.** `window` is a `[Global]`
   object whose named properties sit *below* the prototype chain, so no element
   can shadow `window.fetch`, `window.location`, or `window.toString`.
   `document` is a legacy object with `[LegacyOverrideBuiltIns]`, so an element
   *can* shadow `document.cookie`, `document.title`, even
   `document.getElementById`. Only `document.location` is unforgeable.

2. **Only some tags contribute a name.** An element with an `id` contributes to
   `window`; a `name` contributes only on `embed`, `form`, `img`, `object`.
   The folklore that `<a name=x>` clobbers `window.x` is **false** — anchors only
   contribute to `document.links`/`anchors`.

3. **Declarations decide everything.**

   | Declaration | Bare `X` read | `window.X` read |
   |---|---|---|
   | `var X` / `function X` | safe (own property wins) | safe (own property wins) |
   | `let X` / `const X` / `class X` | safe (lexical binding) | **clobberable** |
   | undeclared | **clobberable** | **clobberable** |

   The `let`/`const` row is the one that bites bundled code: everything lives in
   one module scope, code writes `window.CONFIG`, and the lexical binding is
   invisible to that lookup.

## Browser differences

The model is derived from live measurements of **Chromium 157, Firefox 142, and
WebKit 26** (`data/engine-probe.json`, regenerated by `npm run probe`).

The engines agree on almost everything. The documented divergences:

- **Multiple elements with the same name.** Chrome and WebKit return an
  `HTMLCollection`; **Firefox returns the first `id`-based element as a plain
  element**. So the common mitigation "just render the name twice" defeats
  nesting in Chrome/WebKit but *not* in Firefox:

  ```js
  // Works in Chrome/WebKit: CONFIG is a collection, CONFIG.cdn is undefined.
  // Works in Firefox: CONFIG is the first element, CONFIG.cdn resolves.
  <div id="CONFIG"></div><div id="CONFIG"></div>
  ```

- **`trustedTypes` and `external`** are reachable as window names in some
  engines and not others (Firefox exposes `trustedTypes`; WebKit exposes
  `external`). The tool reports per-engine reachability rather than averaging.

Each finding lists `where:` (engines where the name is reachable) and `safe:`
(the rest), so a fix can be validated engine by engine.

## How it works

```
            ┌──────────────┐   ┌───────────────────┐   ┌───────────────┐
 spec.json →│ page analysis│   │ script extraction │   │ engine model  │
            │  injection   │   │ + taint analysis  │   │ (measured)    │
            │  regions     │   │                   │   │               │
            └──────┬───────┘   └────────┬──────────┘   └───────┬───────┘
                   │                    │                      │
                   └────────────┬───────┴──────────────────────┘
                                ▼
                       ┌──────────────────┐
                       │ exploitability   │→ findings (text / JSON)
                       └──────────────────┘
```

1. **Page analysis** (`src/html/`) parses the page with `parse5`, resolves the
   declared injection regions, and records each region's sanitizer profile
   (`id`/`name` allowed? `form` allowed?).
2. **Extraction** (`src/js/`) parses each script with `acorn`, finds every read
   of a global (bare identifier, `window.X`, `document.X`, computed access,
   destructuring, `this.X`), and records the declaring scope via `eslint-scope`.
3. **Taint** (`src/js/taint.ts`) propagates "derived from a clobberable global"
   through local aliases so `var c = window.CONFIG; s.src = c.cdn` connects the
   read to the sink. Minified bundles need no beautification — names, not
   formatting, are what matter.
4. **Engine model** (`src/model/`) decides, per browser, whether a named element
   can supply the name at all.
5. **Exploitability** (`src/analysis/`) combines a reachable name, an injection
   plan the region permits, and a dangerous usage into a scored finding.

### Value channels

A plan only claims a takeover when the attacker's value is observable the way
the page reads it. This is the single most important source of false positives,
so it is modelled explicitly:

| Page reads | Plan that works | Why |
|---|---|---|
| `CONFIG + ''` | `<a id=CONFIG href=//attacker/>` | `String(anchor)` is the href |
| `CONFIG.cdn.src` | `<form id=CONFIG><img name=cdn src=//attacker/></form>` | `.src` is the URL |
| `CONFIG.cdn.value` | `<form id=CONFIG><input name=cdn value=...></form>` | `.value` is the string |
| `s.src = CONFIG.cdn` | **no plan** | the element stringifies to `[object HTMLInputElement]`, not a URL |

That last row is why a naive "any name is exploitable" tool over-reports: an
input's string form is not its `value`.

## Installation and use

```bash
npm install
npx clobber-scan path/to/spec.json
```

A spec declares the page, its injection regions, and its scripts:

```json
{
  "page": {
    "htmlFile": "page.html",
    "regions": [
      { "name": "reviews", "selector": "#reviews", "profile": "richText" },
      { "name": "bio", "selector": ".profile-bio", "profile": "strictNoIdName" }
    ]
  },
  "scripts": [
    { "id": "bundle.js", "path": "bundle.js" },
    { "id": "app.js", "path": "app.js", "kind": "module" }
  ]
}
```

Paths resolve relative to the spec file; `html` and `code` can be inlined
instead. Profiles:

| Profile | Allows | Use when |
|---|---|---|
| `unsafeInnerHtml` | everything | raw `innerHTML` |
| `richText` | formatting + `img` with `id`/`name`/`src` | typical rich-text sanitizer |
| `strictNoIdName` | tags but no `id`/`name` | hardened sanitizer |
| `naiveFilter` | everything except `script`/`style` | a filter that only blocks scripts |

Options: `--json`, `--out <file>`, `--fail-on <severity>` (CI gate),
`--engines chrome,firefox`, `--help`.

## Verification

The tool is validated two ways.

**Unit tests** (87 total) cover the engine model, extraction shapes (minified,
module, CommonJS, optional chaining, `this`, destructuring), taint, injection
planning, scoring, and precision on real library code.

**Differential browser tests** — the important part. `e2e/differential.test.ts`
takes each fixture page, runs the scanner on it, then **actually loads it in
Chrome, Firefox, and WebKit**, injects the predicted payload, and checks whether
the exploit fires. The scanner and the real engines are independent judges, so
the model cannot drift away from reality without a test failing.

```bash
npm test              # unit tests
bash scripts/setup-browsers.sh   # one-time: download Firefox + WebKit
npm run test:e2e      # 11 pages × 3 engines
npm run test:all
```

The engine model itself is regenerated from live browsers:

```bash
npm run probe         # rewrites data/engine-probe.json
```

## Remediation summary

The tool prints a fix block per finding category. In short:

- **Sanitize the primitive away.** Strip `id` and `name` from every element in
  untrusted regions (e.g. DOMPurify with `FORBID_ATTR: ['id','name']`), and
  strip URL-bearing attributes (`href`, `src`, `data`, `action`) or force them
  through an allowlist. This is the only complete fix.
- **Declare config with `var`/`function`, or assign `window.X = ...`
  explicitly**, before untrusted markup parses. An own property beats named
  access.
- **Never read a top-level `let`/`const` through `window`/`self`/`globalThis`.**
  Use the lexical binding directly.
- **Capture `document` members before rendering untrusted HTML**
  (`const getById = document.getElementById.bind(document)`), or call through
  the prototype.
- **Adopt Trusted Types** so every injection sink needs an explicit policy.

## Limits

- Taint is intra-procedural and flow-insensitive: it may report a *possible*
  flow that a human confirms, but never invents one.
- Regions are declared, not discovered; a route that forwards to a region not in
  the spec will not be analysed.
- Iframes are modelled as contributing a `WindowProxy`; their contents are not
  analysed.
- The builtin lists are a snapshot of the measured browsers. Re-run
  `npm run probe` to refresh.
